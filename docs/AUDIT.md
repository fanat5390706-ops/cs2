# Аудит проекта ХЛТВ 2.0 по ТЗ «аналог HLTV»

Сверка текущей схемы с целевой моделью из промпта. Стек проекта — Django 5.2 + MySQL 8 (см. раздел 6).

## 1. Схема БД: что не так и что исправлено

| Целевая сущность | Что было | Проблема | Решение (этап 1 рефакторинга) |
|---|---|---|---|
| TEAMS: ranking, social links, created/updated | name, tag, country, logo_url | нет соцсетей, дат, места в рейтинге | поля `website/twitter_url/youtube_url/twitch_url/founded_year`, `created_at/updated_at`; рейтинг вынесен в таблицу `team_ranking` |
| Рейтинг как поле `Team.ranking` | — | хранит только «сейчас», нет истории, нельзя иметь несколько рейтингов | `TeamRanking(team, source, valid_on, position, points)` + UNIQUE (team, source, valid_on) и (source, valid_on, position) |
| PLAYERS: real_name, age, current_team, avatar | first_name/last_name, birth_date, TeamMembership | `age` и `current_team` хранить нельзя: устаревают | **оставлено намеренно**: возраст считается от `birth_date`, текущая команда — из `TeamMembership` (left_on IS NULL), уникальность «одна открытая запись» гарантирует GeneratedField. Добавлены `role`, `created_at/updated_at` |
| TOURNAMENTS: organizer, prize_pool, location, tier, logo | `organizer` = FK на **пользователя** | организатор турнира (ESL, BLAST) — не пользователь системы; в ТЗ нет prize_pool/location/tier | `organizer_name`, `prize_pool_usd`, `location`, `tier`; FK `organizer` оставлен как «кто внёс запись» |
| MATCHES: team1_id, team2_id, winner_team_id | `MatchParticipant` (слот 1/2) → `TournamentEntry` → Team; победитель считается во view | в плоской схеме из ТЗ победитель дублирует счёт карт (можно разойтись), а команды без турнира невозможны | **оставлено намеренно** (3НФ): победитель не хранится, считается во view `v_match_series_score`. Добавлен индекс `(status, scheduled_at)` — по нему идут главная, Matches, Results и воркер |
| MAPS | `GameMap` (справочник) + `MatchMap` + `MatchMapScore` | в ТЗ одна таблица со счётом в строке карты: теряется ограничение «ровно две стороны» | оставлено |
| PLAYER_STATS: rating, kast, adr | `PlayerMapStat` хранит сырое (kills, deaths, damage, rounds) | rating/adr — производные, хранить нельзя (аномалии обновления) | оставлено; rating считается в запросе. **KAST не считается**: нужны данные по раундам, их нет ни в одном бесплатном API |
| TeamStats | нет | — | не таблица: считается из `v_tournament_standings` и результатов. Если нагрузка вырастет — материализованная таблица, обновляемая воркером |
| News, Videos | есть | — | ок; у `NewsArticle` есть индекс по дате |

## 2. Производительность
- Добавлен индекс `ix_match_status_time`. Остальные индексы (tournament+time, membership player/team) уже есть.
- N+1: `attach_logos` и `with_team_logos` делают по одному доп. запросу на страницу (не на строку); название события добавлено тем же способом.
- Списки пагинируются (50 / 48 на страницу), матчи ограничены LIMIT 200.
- Риск: представления MySQL (`v_*`) пересчитываются при каждом запросе. До десятков тысяч матчей это нормально; дальше — кэш или материализация.

## 3. API
Есть `/api/…` (teams, players, tournaments, matches, news, videos, streams), только чтение, limit ≤ 100. Отличие от примера в ТЗ: `/api/matches/<id>/`, а не `/api/match/{id}` — во множественном числе везде единообразно (REST-соглашение).

## 4. Безопасность
- Ключи только в `.env`, `.env.example` с заглушками. ✔
- Раскрытые в переписке ключи (Steam, PandaScore, FACEIT, YouTube) нужно **перевыпустить**, если репозиторий или скриншоты попадали к третьим лицам.
- CORS `*` допустим, так как API только на чтение и без cookie-авторизации.
- Регистрация зрителя: группа «Зритель», без `is_staff`. ✔
- `DEBUG` и `SECRET_KEY` берутся из окружения; для выкладки нужны `ALLOWED_HOSTS` и HTTPS.

## 5. Фоновые задачи и кэш
Сейчас `run_workers` (цикл + расписание по ключам). Это заменяет Celery для одной машины. Redis не нужен, пока нет сотен посетителей в минуту: главная — это 8–10 лёгких SQL-запросов, плюс есть встроенный кэш Django (LocMem/файловый) как следующий шаг без новых сервисов.

## 6. Стек: Django vs FastAPI + SQLAlchemy + Redis + Celery
Промпт предлагает другой стек. Я **не** переписываю проект на него, потому что:
1. работа — учебная, защита идёт по уже построенной и согласованной модели (Django ORM, миграции, Admin как интерфейс ввода данных);
2. почти всё, что даёт новый стек, у нас есть: REST API, фоновые воркеры, кэш можно подключить штатно;
3. переписывание = недели работы без новой функциональности для пользователя.
Если для защиты нужен именно FastAPI — это отдельное решение: тогда схема БД остаётся (она не зависит от ORM), а переписываются слой доступа и API. Скажите, и я составлю план.

## 7. План дальнейшего рефакторинга
1. ✔ Схема: поля Team/Tournament/Player, `team_ranking`, индекс матчей.
2. Свой рейтинг команд (Elo по серии результатов) → заполняет `team_ranking`, блок «Top 10 teams» на главной.
3. Страница команды: `Team information`, `Current lineup`, соцсети, место в рейтинге.
4. Страница турнира: призовой фонд, тир, место проведения.
5. Страница игрока: роль, история команд и матчей.
6. Кэш главной (Django cache, TTL 60 с).

## 8. Рейтинг команд: источник данных (обновление)
Собственный Elo по нескольким серий из БД давал недостоверные места (мало матчей, малая выборка), поэтому на сайте он больше
не показывается. Мировой рейтинг берётся из официального публичного репозитория Valve
(Valve Regional Standings, `live/<год>/standings_global_*.md`) командой `sync_vrs`, раз в сутки, в таблицу `team_ranking`
(source = `vrs`). Если команды из рейтинга нет в нашей БД, сохраняется её название и состав (`team_name`, `roster`).
Команда `compute_ranking` оставлена как учебный пример расчёта Elo, но в воркерах и интерфейсе не используется.
